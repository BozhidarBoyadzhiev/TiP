# Codebase map

Spring Boot 4 monolith, package by feature under `dev.tip`. A feature uses another feature only through its `api` subpackage or Spring events; `ArchitectureTest` enforces it.

## Runtime and deployment

Runs on Render as one Docker container (`Dockerfile`: exec form `java -jar`, so the JVM is PID 1 and gets `SIGTERM`; `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75`). `application.properties` listens on `PORT` (8080 without it; `SERVER_PORT` wins), caps the Hikari pool at `TIP_DB_POOL_SIZE` (5), and uses `server.forward-headers-strategy=native`: Tomcat's `RemoteIpValve` trusts `X-Forwarded-*` only from private addresses and takes the rightmost untrusted `X-Forwarded-For` entry as the client, so `getRemoteAddr()` is the real client for every rate limit, HTTP and WebSocket alike, and a forwarded `https` request is secure. `TIP_CLIENT_IP_HEADER` (bound to `server.tomcat.remoteip.remote-ip-header`) picks another header such as `True-Client-IP`; `ClientIpValve` runs in front of the `RemoteIpValve` and drops such a single value header unless it is sent once with exactly one IP literal, so the connection address is the client then. `TIP_DEBUG_CLIENT_IP` turns on `ClientIpDiagnostics`, a temporary log line per `/api/public/` request (connection and resolved address, raw proxy headers). Health probes are off, so `/actuator/health` answers only `{"status":"UP"}` (database, disk space, ping, ssl; never PayPal or Anthropic). `docs/DEPLOYMENT.md` has the variables, health path, deploy flow and smoke test.

## Security filter chains

1. `OwnerSecurityConfig` (order 1) matches `/owner`, `/owner/**`, `/api/owner/**`, `/ws/owner`, `/judges/**` and `/demo/**`. Form login, CSRF on, request cache off. `GET /judges`, `GET /demo`, `POST /judges/session`, `POST /demo/session` and `/judges/resume` (the page for any method Spring routes to it, and its post) are open; everything else needs an owner. Unauthenticated pages redirect to `/owner/login`; the API and the owner channel answer 401 problem details. `OwnerAccessFilter` runs after authorisation (sandbox expiry, read only demo). Sign out publishes `OwnerSignedOut`, except for the read only demo, and `SignOutTarget` picks where the browser goes by the owner's kind.
2. `SecurityConfig` (lowest order) matches everything else. Public paths are listed (including `/p/**` and `/ws/**`, whose handshake interceptors do their own checks); the static files (`/css/**`, `/js/**`, `/fonts/**`, `/icons/**`, `/images/**`, `/favicon.ico`) also allow `HEAD`, which answers the `GET`'s status, content type and cache headers without a body, while pages and every other path keep `GET` only; the rest is 403 problem details, except that a browser `GET` (`NotFoundPage.wantedBy`) gets the 404 page, which tells a visitor nothing more than a 403. CSRF ignored for `/api/public/**` and `/webhooks/**`.

Both apply `SecurityDefaults`: CSP with nonce (`connect-src` also names the request's own `ws:`/`wss:` origin), HSTS, referrer policy, problem details for 403 (`FORBIDDEN`, `CSRF_TOKEN_INVALID`).

## How a tip flows

1. The phone opens `/t/{slug}`; `tip.js` loads the device config and the PayPal JS SDK. The page (one card: brand, presets in rows of three with the last row stretched, an own amount stepper, the paper note with the peeking panda, the "You're tipping" line and PayPal's vertical gold buttons) formats money with `Intl.NumberFormat` in the device's currency, whole amounts without decimals. The own amount is parsed into minor units by joining digit strings, never through floating point (`7`, `7.5`, `7.50`, `7,50`; more decimals rejected). While there is no valid amount the PayPal buttons are disabled with the SDK's `onInit` actions and `onClick` rejects. Errors show as a paper note with a friendly sentence and Try again; a capture shows the success note with the amount and a link to `/p/{slug}`. Under the buttons the card's foot links to the public sample dashboard (`/demo`).
2. PayPal's `createOrder` callback posts to `/api/public/devices/{slug}/tips`. `TipService` validates amount and currency, sanitises the message, saves a `CREATED` tip, calls `PayPalGateway.createOrder` (request id `create-<tipId>`, `custom_id` = tip id) and stores the order id. PayPal failure marks the tip `FAILED`.
3. After approval, `onApprove` posts to `/api/public/tips/{tipId}/capture`. `TipService` captures the stored order (request id `capture-<tipId>`); `ORDER_ALREADY_CAPTURED` is reconciled with `lookupOrder`.
4. PayPal also sends `PAYMENT.CAPTURE.*` webhooks. `PayPalWebhookController` verifies the raw body, then `PayPalWebhookProcessor` inserts the event row (`ON CONFLICT DO NOTHING`) and applies the transition in one transaction: `COMPLETED` captures, `PENDING` pends, `DENIED` and `DECLINED` fail, `REFUNDED` refunds, `REVERSED` reverses.
5. Both paths call `TipTransitions`. Its conditional `UPDATE ... WHERE status IN (...)` lets exactly one caller win; only the winner publishes `TipCaptured`, which listeners receive after commit.
6. `TipCapturedListener` runs `TipReactionWorker` on the AI executor: claim the tip with a conditional update, call Claude (or skip when there is no message or AI is disabled), then a final write conditional on the same claim stores `message_kind`, `reaction` (`PLAIN` when flagged, otherwise the kind), the flag and `owner_note` (`REQUEST` only), plus the language, translation, song and song key (kept for a flagged message too, for the owner to see if they overrule the flag), and publishes `TipReacted` after commit with `repeats` from `tip.amount_minor` and its currency (`ReactionRepeats`, 1 when flagged). Skipped tips store `PLAIN` with no kind. A failed or skipped model call (`ModelUnavailable`: an API error, a timeout, or the breaker resting) stores `PLAIN` with repeats 1 as `UNAVAILABLE` at once and is never retried; an invalid answer goes back to `PENDING`, and the third stores `PLAIN` as `FAILED`. `AiRecoveryJob` reruns the flow for pending tips and expired claims.
7. `AbandonedTipsJob` marks `CREATED` tips older than 6 hours `ABANDONED` every 10 minutes.

## How a reaction reaches the panda

1. `TipReactions` publishes `TipReacted` after commit. `ReactionDispatcher` handles it on the delivery executor (virtual threads), never on the publisher's thread, which still holds the committed transaction's connection.
2. It inserts the `reaction_delivery` row, with its repeats, using `ON CONFLICT (tip_id) DO NOTHING`; no row inserted means a duplicate, and nothing more happens.
3. If the device has a session in `DeviceSessions`, `ReactionSender` sends `{type: reaction, id, reaction, repeats, at}` and records the send. Then `ObserverSessions` broadcasts `{type, reaction, repeats, at}` to the slug's observers. Resends and replays send the stored repeats.
4. The device acks with `{type: ack, id}` on receipt, before playing; the update is conditional on the session's own device and `acked_at is null`.
5. `ReactionResendJob` resends to connected devices every second: unacked, fewer than 4 sends, last send 5 s ago, under 60 s old. A device that connects is registered pending, replacing any old session (sent `{type: closing, reason: replaced}`, then closed with 4000), and is marked connected (`last_seen_at` stored); then it gets `hello`, its session becomes ready for live sends, and the replay sends its unacked reactions of the last 60 s, oldest first. `hello` is always the first message: a reaction stored while the session is pending is skipped by the dispatcher and comes with the replay. The dispatcher sends only after its own `REQUIRES_NEW` insert of the delivery row has committed, so the replay, which runs after the session is ready, always sees a reaction the dispatcher skipped.
6. `SessionKeepalive` pings every device and observer session every 20 s and closes those without a pong for 45 s with 1001. On shutdown it closes every session with 1001. Device sessions get `closing` with `timeout` or `shutdown` first, because Render's proxy delivers every close as 1005 and the code never reaches the device.

The virtual panda (`/p/{slug}`) is an inline SVG of the seated cardboard giant panda (black ears, arms and feet, white head and body) holding the gold TiP coin, under the TiP brand button that unfolds into "Tip integrated Panda" on hover, focus or tap. It loads the device name from `/api/public/devices/{slug}` and shows it under the panda unless it is "TiP" or "Tip integrated Panda", opens `/ws/observe/{slug}` and plays the protocol's four patterns on `requestAnimationFrame` in their colours (`WARM` pink, `PLAYFUL` yellow, `REQUEST` blue, `PLAIN` soft white), each a unit played `base + (repeats - 1)` times with its gap, the client policy of `docs/DEVICE_PROTOCOL.md` (queue of 8 waiting, dropping the oldest waiting; backoff 1 to 60 s with up to 20 % taken off, reset only after 60 s connected), captions and connection status. The light is on the coin only: each frame's level sets the opacity of `#panda-coin-glow` and `#panda-coin-sparkle`, and 0.35 of it on `#panda-coin-light`; the colour is `--light` on the SVG. With `prefers-reduced-motion` it holds a steady coin light for the scaled pattern's length and drops the idle animations and the brand's transitions.

The panda art: `src/test/resources/art/panda-sprite.svg` is the canonical source of the drawn panda (for now a byte identical copy of the approved `briefs/assets/08-panda/panda-sprite.svg`; the build reads only the copy), a giant panda in cardboard (symbols `head` 132 × 74, `eyes-open`, `eyes-shut`, `paws-eyes`, `paws` 132 × 22, `face` 64 × 64 for icons). Each page that draws it (tip, 404, judge code, resume, owner login, dashboard) carries the symbols it uses inline in a hidden `svg.sprite` and draws the peek, eyes and paws with `<use href>`; pupils that move and the dozing lids are groups and rects around `eyes-open`. `PandaArtTest` fails the build when a page's copy differs from the sprite beyond whitespace. The panda page draws `panda-sitting.svg` inline instead.

Shared page parts: `static/css/brand.css` (colour tokens, `.sprite`, the brand button and its unfold, the paper note with the peeking panda and paws) and `static/js/brand.js` (splits and measures the brand letters, tap toggle, `TipBrand.isBrandName`: "TiP" or "Tip integrated Panda" ignoring case and whitespace) are used by the tip, panda and 404 pages; the owner pages use `brand.css` too, with their own small brand letters.

Page heads: the tip, panda, 404, owner login and dashboard pages link `/favicon.ico` (48x48), `/icons/favicon-panda.svg` and the apple touch icon, set `theme-color` `#120c09` and have fixed titles with the brand first (`TiP | Leave a tip`, `TiP | Panda`, `TiP | Not found`, `TiP | Owner login`, `TiP | Dashboard`); no script changes `document.title`. Only the tip and panda pages carry link preview tags (`og:type`, `og:site_name`, `og:title`, `og:description`, `og:url`, `og:image` with its size, type and alt, `twitter:card` `summary_large_image`), all fixed text except the `{{OG_URL}}` and `{{OG_IMAGE}}` placeholders that `LinkPreview` fills; nothing from the request or the database goes into the head.

Fonts: `static/fonts/fonts.css` holds the `@font-face` rules for self hosted Fredoka (400 to 700, Latin and Latin Extended woff2 in `static/fonts/fredoka/` with `OFL.txt`); `/fonts/**` is public in `SecurityConfig` and `default-src 'self'` covers fonts. Pages make no third party requests apart from the PayPal JS SDK on the tip page. Caching: woff2 font files, icons and the preview image are `public, max-age=2592000` (30 days), since they never change; a changed asset gets a new file name. CSS (`fonts.css` included) and JS are `no-cache` with `Last-Modified`: browsers store them but revalidate, and an unchanged file answers 304. HTML pages (tip, panda, 404 and the owner pages) are `no-store`, set by their controllers and `NotFoundPage`, because each carries its request's CSP nonce.

## Tools

`src/tools/java/dev/tip/tools` is its own Gradle source set (`tools`), not in the app jar. It compiles against the app's classes and dependencies. `./gradlew fakeDevice --args="--url=ws://localhost:8080 --device=<uuid> [--secret=<secret>]"` runs `FakeDevice`, which reads `.env` like `bootRun` and falls back to `TIP_DEMO_DEVICE_SECRET`. `FakeDevice` (JDK `HttpClient` WebSocket, listener, acks every reaction on receipt including repeats it does not play, reads `repeats` with missing as 1 and clamping, acks an unknown kind and plays it as `PLAIN` with repeats 1, prints a `closing` reason and waits at least 60 s after `replaced`, stops on 401), `Player` (queue of 8, drops the oldest waiting, plays in order), `LedPattern` (protocol units, gaps, base units, scaled lengths and a text picture), `RecentIds` (last 16 tip ids), `Backoff` (the client policy: 1 s doubling to 60 s, up to 20 % taken off, reset only after 60 s connected).

`./gradlew newAccessCode -Plabel=<label> -Pexpires=<ISO 8601 with offset>` runs `NewAccessCode`: a code from `SecureRandom` through `AccessCode`, printed once with its `TIP_ACCESS_CODES` entry; nothing is written to a file; a bad label or expiry exits 2 without a code.

`./gradlew aiEval` runs `AiEval`: it binds `tip.ai.*` from `application.properties` and the environment (`.env` loaded by the task), builds the production classifier through `dev.tip.ai.EvalClassifier`, runs the labelled cases in `src/tools/resources/ai-eval-cases.jsonl` (message, kind or a list of accepted kinds, flagged, ownerNote `true`, `false` or `"ifRequest"`, and optionally `language` (a code, or a list of codes any of which counts, for a message that mixes two), `translation` (whether an English text should be there) and `song` (a title, or null for none)) one by one against the real model, and prints each disagreement and accuracy for kind (over the unflagged cases only: a flagged message's kind is not scored), flag, owner note and all three, then language (exact), translation (present when it should be) and song (case insensitive) over the cases that label them. It decodes each line as strict UTF-8 and fails with the line number on a malformed byte or a broken line. The cases include prompt injection attempts (fake system lines, fake JSON results, delimiter breakouts, owner impersonation, one in French, two hidden in a "translate this" request). Without a key it exits with a message. Never part of `build`, `check` or CI.

Every `JavaExec` task runs with `-Dstdout.encoding=UTF-8` and `-Dstderr.encoding=UTF-8`: Gradle reads a tool's output as UTF-8, and a JVM writing to a pipe on Windows otherwise encodes in Cp1252, which turned `ö` into U+FFFD. `.editorconfig` and `.gitattributes` keep text files UTF-8 with LF (CRLF for `.ps1` and `.bat`). Windows PowerShell 5.1 still needs `[Console]::OutputEncoding = [Text.Encoding]::UTF8` to display the output.

## Firmware

`firmware/` is a PlatformIO project for the physical panda (ESP32 DevKit `esp32dev`, Arduino core 3.3.12 through the pioarduino platform pinned in `platformio.ini`, partition table `huge_app.csv`). It sits outside the Gradle build: nothing in `build.gradle.kts` or Spotless reads it, and `firmware/.pio/` is git ignored. CI builds it and runs its native tests in the `firmware` job. `firmware/README.md` has setup, secrets, build, flash, monitor, test, the library choice and the TLS statement. `THIRD_PARTY_NOTICES.md` carries the notices of what the firmware ships: the Arduino ESP32 core (LGPL 2.1), ESP-IDF (Apache 2.0) and the third party components the linker map shows inside the image (lwIP with its PPP licences, Mbed TLS, FreeRTOS, the Xtensa HAL, wpa_supplicant, TLSF, cJSON, newlib, the GCC runtime), links2004/WebSockets (LGPL 2.1), ArduinoJson (MIT) and the BSD 3-Clause PN532 code ported into `tip_type4_tag`. `LICENSES/` holds the full text of every licence it names; a change of the pinned platform or libraries needs the list checked again against `firmware/.pio/build/esp32dev/firmware.map`.

- `include/tip_config.h` (committed): server host and port, `TIP_PUBLIC_BASE_URL` (`https://` and the host), device slug, `TIP_NFC_BAUD` (115200, or 921600 by build flag), SNTP servers and every timing and limit, the NFC retries and re-arm times among them. `include/secrets.h` (git ignored, template `secrets.example.h`): WiFi, `TIP_DEVICE_ID`, `TIP_DEVICE_SECRET`; the build stops without it.
- `lib/tip_core/` (plain C++, no Arduino includes, Unity tests in `test/` run with `pio test -e native`): `tip_protocol` (parse server messages from a filtered 256 byte `StaticJsonDocument`, build acks), `tip_intake.h` (`RecentIds` ring of 16, ack always and play once), `tip_player.h` (queue of 8 dropping the oldest waiting, LED level over time), `tip_patterns` (the four patterns with the virtual panda's step timings, status flicks), `tip_link` (backoff, silence check, HTTP status line, certificate dates), `tip_ndef` (`buildTipUrl`: base URL plus `/t/` plus slug, https with a lowercase host and a `DeviceSlug` slug only, refused past a length; `buildUriMessage`: one short NDEF URI record), `tip_type4_tag` (read only NFC Forum Type 4 tag: SELECT and READ BINARY, reads bounded by the selected 15 byte capability container or 128 byte NDEF file; ported from Seeed-Studio/PN532, BSD-3-Clause notice in the file), `tip_pn532_frame` (PN532 normal frames built with their checksums, a byte by byte `FrameReader` for ACK, NACK, error and information frames, `unpackResponse` checking direction and response code), `tip_alive_check` (`aliveCheck`: wait, probe, or restart the timer when a field was seen in the last 5 s).
- `src/log.cpp`: `logLine`, the only writer to serial: formats each line into a local buffer and writes it under a mutex; ESP-IDF logging is routed through it and the Arduino HAL's raw `log_e` is off (`CORE_DEBUG_LEVEL=0`).
- `src/main.cpp` starts three tasks on core 1: `network_task.cpp` (`net`, priority 2: WiFi, SNTP, WebSocket state machine, ack, hand over; logs its longest pause between steps every minute) and `playback_task.cpp` (`led`, priority 3: the only code that writes the LED, every 10 ms), joined by a FreeRTOS queue of `tip::Reaction`, and `nfc_task.cpp` (`nfc`, priority 1), which shares nothing with them.
- `src/nfc_task.cpp`: builds the tag's URL from `TIP_PUBLIC_BASE_URL` and `TIP_DEVICE_SLUG` (a `static_assert` checks it fits the NDEF file; an invalid one turns NFC off), finds the PN532 on UART2 (GPIO16 RX, GPIO17 TX) at the build's speed or the other, moves it to the build's speed, then arms the tag, answers each tap's APDUs through `Type4Tag`, keeps it off 3 s after a read and until the field is gone for 100 ms, resyncs (wake-up and SAMConfig, 6 tries) after a failure, checks every 30 s while armed that the PN532 still answers (skipped, and the 30 s started over, when a field was seen in the last 5 s; the timer runs across taps, since an armed tag sees no field), and looks for a missing or silent PN532 again from 1 s doubling to every 30 s. `src/pn532.cpp`: the PN532 over HSU (`Pn532`: frames out, ACK and answers back, every wait a `vTaskDelay(1)` poll, a 512 byte transmit buffer so `write()` never waits for the wire) and the commands the tag needs.
- `src/secure_transport.cpp` is the TLS client under links2004/WebSockets 2.7.1 in `NETWORK_CUSTOM` mode: `NetworkClientSecure` with the built in CA bundle and hostname check, then the validity dates of every presented certificate against SNTP time before the library sends the upgrade request; it also reads the HTTP status line, so a 401 stops reconnects.

`firmware/spikes/pn532/` is a separate PlatformIO project from brief 05c, kept as evidence after brief 05d moved the tag into the main firmware (same platform and core, not built by CI, `.pio/` git ignored): a PN532 on UART2 (GPIO16/17, 115200 or 921600 baud) in its own task, either emulating a Type 4 tag with the demo panda's tip URL (`emulate`: `type4_tag` answers the APDUs, `pn532_target` sends the PN532 commands, re-armed 3 s after each read once the field is gone) or writing that URL to an NTAG215 (`write_tag`), with a heartbeat in `loop()`. Its `README.md` has the wiring, run steps, library notes and the tap results.

Device side of the protocol: connect to `wss://<host>/ws/device/{deviceId}` with `Authorization: Bearer <secret>` and no `Origin`; `hello` is logged; each `reaction` is validated (lowercase uuid id, known kind or `PLAIN` x1 for an unknown one, `repeats` missing or not an integer as 1, clamped to 1 to 5), acked with `{type: ack, id}` on receipt, and played unless its id is among the last 16; `closing` is logged and `replaced` makes the next wait at least 60 s; anything else is logged, malformed messages are not acked. Nothing received for 45 s closes the connection. Reconnects back off from 1 s doubling to 60 s with up to 20 % jitter taken off, reset only after a connection stayed up 60 s; a 401 retries every 10 minutes with the rejected status pattern.

## How a refund flows

1. A signed in owner posts `/api/owner/tips/{tipId}/refund` with the CSRF token.
2. `TipRefundService` checks the tip's device belongs to the owner through `DeviceDirectory.isOwnedBy` (404 otherwise), that it is not a sample tip (409 `DEMO_TIP`) and that it is `CAPTURED` (409 otherwise).
3. `PayPalGateway.refundCapture` refunds in full with request id `refund-<tipId>`. `COMPLETED` (or `CAPTURE_FULLY_REFUNDED`) runs `TipTransitions.refund`; `PENDING` answers 202 and the `PAYMENT.CAPTURE.REFUNDED` webhook runs the same transition later.

## Startup seeding

`DemoDeviceSeeder` creates the demo owner through `OwnerProvisioning` when the email is new and never changes an existing owner (password hash, display name, time zone), then creates the demo device when its slug is new, owned by that owner. An existing device that belongs to another owner stays with that owner in every profile but `dev`, with one WARN naming the slug and both owner ids; only under `dev` is it moved to the demo owner (`DEV_PROFILE`, checked through the `Environment`). On the demo owner's own device the secret hash is replaced only when it does not match `TIP_DEMO_DEVICE_SECRET`, logged at INFO, so changing the variable rotates the secret in every profile and a restart with the same secret leaves the stored hash byte identical; an existing device's name is never changed. It refuses a secret that is clearly not random and logs the demo device id, never the secret or an email.

`SampleTipSet` is the one sample set, used by dev, every sandbox and the public demo. 28 invented tips (no real song, artist or brand): the four kinds and the four visible statuses, tips without a message, requests and feedback with owner notes, French, Spanish and German messages with translations, one invented song ("Marmalade Moonwalk") in three spellings sharing a key, and two hidden messages, one in Bulgarian with its translation and one in English. Today's are placed at shares of the time since local midnight in the owner's zone, so there are always several today; the rest at fixed local times on the two days before. Each is `demo`, without PayPal ids, stored as the AI would have left it (`DONE`, `SKIPPED` without a message, `PENDING` for the pending payment), with an acked delivery at the resend limit (except `WITHOUT_DELIVERY`, so `repeats` shows null too) and repeats from `ReactionRepeats`; today's `owner_digest` row holds pre-written bullets and request groups covering every shown request of the week, so no model call fills a sandbox. `refresh` deletes the device's sample tips and deliveries and the owner's digests and seeds again, unless the device has a sample tip from today; real tips are never touched. It writes `tip` and `reaction_delivery` with its own SQL, so a migration that changes their columns, or the resend and replay rules, must update it.

With the Spring profile `dev` (local runs only; Render never sets it), `DevTipSeeder` calls `SampleTips.refresh` for the demo device on `ApplicationReadyEvent`, which comes after every `ApplicationRunner`, so the demo device exists by then: the same day changes nothing, a later day gets a fresh set. Without a demo device it logs a warning and adds nothing.

`PublicDemo` makes the public demo at startup and refreshes its samples then and every night at 00:05 London time.
