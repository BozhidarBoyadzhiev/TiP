# Codebase map

Spring Boot 4 monolith, package by feature under `dev.tip`. A feature uses another feature only through its `api` subpackage or Spring events; `ArchitectureTest` enforces it.

## Runtime and deployment

Runs on Render as one Docker container (`Dockerfile`: exec form `java -jar`, so the JVM is PID 1 and gets `SIGTERM`; `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75`). `application.properties` listens on `PORT` (8080 without it; `SERVER_PORT` wins), caps the Hikari pool at `TIP_DB_POOL_SIZE` (5), and uses `server.forward-headers-strategy=native`: Tomcat's `RemoteIpValve` trusts `X-Forwarded-*` only from private addresses and takes the rightmost untrusted `X-Forwarded-For` entry as the client, so `getRemoteAddr()` is the real client for every rate limit, HTTP and WebSocket alike, and a forwarded `https` request is secure. `TIP_CLIENT_IP_HEADER` (bound to `server.tomcat.remoteip.remote-ip-header`) picks another header such as `True-Client-IP`; `ClientIpValve` runs in front of the `RemoteIpValve` and drops such a single value header unless it is sent once with exactly one IP literal, so the connection address is the client then. `TIP_DEBUG_CLIENT_IP` turns on `ClientIpDiagnostics`, a temporary log line per `/api/public/` request (connection and resolved address, raw proxy headers). Health probes are off, so `/actuator/health` answers only `{"status":"UP"}` (database, disk space, ping, ssl; never PayPal or Anthropic). `docs/DEPLOYMENT.md` has the variables, health path, deploy flow and smoke test.

## Security filter chains

1. `OwnerSecurityConfig` (order 1) matches `/owner`, `/owner/**`, `/api/owner/**`. Form login, CSRF on, request cache off. Unauthenticated pages redirect to `/owner/login`; the API answers 401 problem details.
2. `SecurityConfig` (lowest order) matches everything else. Public paths are listed (including `/p/**` and `/ws/**`, whose handshake interceptors do their own checks); the static files (`/css/**`, `/js/**`, `/fonts/**`, `/icons/**`, `/images/**`, `/favicon.ico`) also allow `HEAD`, which answers the `GET`'s status, content type and cache headers without a body, while pages and every other path keep `GET` only; the rest is 403 problem details, except that a browser `GET` (`NotFoundPage.wantedBy`) gets the 404 page, which tells a visitor nothing more than a 403. CSRF ignored for `/api/public/**` and `/webhooks/**`.

Both apply `SecurityDefaults`: CSP with nonce (`connect-src` also names the request's own `ws:`/`wss:` origin), HSTS, referrer policy, problem details for 403 (`FORBIDDEN`, `CSRF_TOKEN_INVALID`).

- `device`: owner_id (not null, foreign key), secret_hash (32 bytes)

`V3__reaction_delivery.sql`:
- `reaction_delivery`: tip_id primary key, device_id, reaction (check constrained), reacted_at, sent_count, last_sent_at, acked_at; partial index on (device_id, reacted_at) where acked_at is null. No foreign key to `tip`, which `devices` does not own.
- Deletes the V2 placeholder owner when it owns no devices.

`V4__reaction_model.sql`:
- `tip`: message_kind and owner_note (varchar 100), both null; message_kind and reaction checked against `WARM`, `PLAYFUL`, `REQUEST`, `PLAIN`
- `reaction_delivery`: reaction checked against the same four values
- Existing rows: `POSITIVE` becomes `WARM`, `NEUTRAL` and `NEGATIVE` become `PLAIN`; classified (`DONE`) tips get the same message_kind

`V5__reaction_repeats.sql`:
- `reaction_delivery`: repeats smallint, default 1 (existing rows), checked 1 to 5

## How a tip flows

1. The phone opens `/t/{slug}`; `tip.js` loads the device config and the PayPal JS SDK. The page (one card: brand, presets in rows of three with the last row stretched, an own amount stepper, the paper note with the peeking panda, the "You're tipping" line and PayPal's vertical gold buttons) formats money with `Intl.NumberFormat` in the device's currency, whole amounts without decimals. The own amount is parsed into minor units by joining digit strings, never through floating point (`7`, `7.5`, `7.50`, `7,50`; more decimals rejected). While there is no valid amount the PayPal buttons are disabled with the SDK's `onInit` actions and `onClick` rejects. Errors show as a paper note with a friendly sentence and Try again; a capture shows the success note with the amount and a link to `/p/{slug}`.
2. PayPal's `createOrder` callback posts to `/api/public/devices/{slug}/tips`. `TipService` validates amount and currency, sanitises the message, saves a `CREATED` tip, calls `PayPalGateway.createOrder` (request id `create-<tipId>`, `custom_id` = tip id) and stores the order id. PayPal failure marks the tip `FAILED`.
3. After approval, `onApprove` posts to `/api/public/tips/{tipId}/capture`. `TipService` captures the stored order (request id `capture-<tipId>`); `ORDER_ALREADY_CAPTURED` is reconciled with `lookupOrder`.
4. PayPal also sends `PAYMENT.CAPTURE.*` webhooks. `PayPalWebhookController` verifies the raw body, then `PayPalWebhookProcessor` inserts the event row (`ON CONFLICT DO NOTHING`) and applies the transition in one transaction: `COMPLETED` captures, `PENDING` pends, `DENIED` and `DECLINED` fail, `REFUNDED` refunds, `REVERSED` reverses.
5. Both paths call `TipTransitions`. Its conditional `UPDATE ... WHERE status IN (...)` lets exactly one caller win; only the winner publishes `TipCaptured`, which listeners receive after commit.
6. `TipCapturedListener` runs `TipReactionWorker` on the AI executor: claim the tip with a conditional update, call Claude (or skip when there is no message or AI is disabled), then a final write conditional on the same claim stores `message_kind`, `reaction` (`PLAIN` when flagged, otherwise the kind), the flag and `owner_note` (unflagged `REQUEST` only), and publishes `TipReacted` after commit with `repeats` from `tip.amount_minor` and its currency (`ReactionRepeats`, 1 when flagged). Skipped tips store `PLAIN` with no kind. A failed attempt goes back to `PENDING`; the third failure stores `PLAIN` as `FAILED`. `AiRecoveryJob` reruns the flow for pending tips and expired claims.
7. `AbandonedTipsJob` marks `CREATED` tips older than 6 hours `ABANDONED` every 10 minutes.

## How a reaction reaches the panda

1. `TipReactions` publishes `TipReacted` after commit. `ReactionDispatcher` handles it on the delivery executor (virtual threads), never on the publisher's thread, which still holds the committed transaction's connection.
2. It inserts the `reaction_delivery` row, with its repeats, using `ON CONFLICT (tip_id) DO NOTHING`; no row inserted means a duplicate, and nothing more happens.
3. If the device has a session in `DeviceSessions`, `ReactionSender` sends `{type: reaction, id, reaction, repeats, at}` and records the send. Then `ObserverSessions` broadcasts `{type, reaction, repeats, at}` to the slug's observers. Resends and replays send the stored repeats.
4. The device acks with `{type: ack, id}` on receipt, before playing; the update is conditional on the session's own device and `acked_at is null`.
5. `ReactionResendJob` resends to connected devices every second: unacked, fewer than 4 sends, last send 5 s ago, under 60 s old. A device that connects gets `hello`, replaces any old session (sent `{type: closing, reason: replaced}`, then closed with 4000) and gets its unacked reactions of the last 60 s, oldest first.
6. `SessionKeepalive` pings every device and observer session every 20 s and closes those without a pong for 45 s with 1001. On shutdown it closes every session with 1001. Device sessions get `closing` with `timeout` or `shutdown` first, because Render's proxy delivers every close as 1005 and the code never reaches the device.

The virtual panda (`/p/{slug}`) is an inline SVG of the seated cardboard bear holding the gold TiP coin, under the TiP brand button that unfolds into "Tip integrated Panda" on hover, focus or tap. It loads the device name from `/api/public/devices/{slug}` and shows it under the bear unless it is "TiP" or "Tip integrated Panda", opens `/ws/observe/{slug}` and plays the protocol's four patterns on `requestAnimationFrame` in their colours (`WARM` pink, `PLAYFUL` yellow, `REQUEST` blue, `PLAIN` soft white), each a unit played `base + (repeats - 1)` times with its gap, queue of 4, captions, connection status and backoff. The light is on the coin only: each frame's level sets the opacity of `#panda-coin-glow` and `#panda-coin-sparkle`, and 0.35 of it on `#panda-coin-light`; the colour is `--light` on the SVG. With `prefers-reduced-motion` it holds a steady coin light for the scaled pattern's length and drops the idle animations and the brand's transitions.

Shared page parts: `static/css/brand.css` (colour tokens, the brand button and its unfold, the paper note with the peeking panda and paws) and `static/js/brand.js` (splits and measures the brand letters, tap toggle, `TipBrand.isBrandName`: "TiP" or "Tip integrated Panda" ignoring case and whitespace) are used by the tip, panda and 404 pages.

Page heads: the tip, panda, 404 and owner login pages link `/favicon.ico` (48x48), `/icons/favicon.svg` and the apple touch icon, set `theme-color` `#120c09` and have fixed titles with the brand first (`TiP | Leave a tip`, `TiP | Panda`, `TiP | Not found`, `TiP | Owner login`); no script changes `document.title`. Only the tip and panda pages carry link preview tags (`og:type`, `og:site_name`, `og:title`, `og:description`, `og:url`, `og:image` with its size, type and alt, `twitter:card` `summary_large_image`), all fixed text except the `{{OG_URL}}` and `{{OG_IMAGE}}` placeholders that `LinkPreview` fills; nothing from the request or the database goes into the head.

Fonts: `static/fonts/fonts.css` holds the `@font-face` rules for self hosted Fredoka (400 to 700, Latin and Latin Extended woff2 in `static/fonts/fredoka/` with `OFL.txt`); `/fonts/**` is public in `SecurityConfig` and `default-src 'self'` covers fonts. Pages make no third party requests apart from the PayPal JS SDK on the tip page. Caching: woff2 font files, icons and the preview image are `public, max-age=2592000` (30 days), since they never change; a changed asset gets a new file name. CSS (`fonts.css` included) and JS are `no-cache` with `Last-Modified`: browsers store them but revalidate, and an unchanged file answers 304. HTML pages (tip, panda and 404) are `no-store`, set by their controllers and `NotFoundPage`, because each carries its request's CSP nonce.

## Tools

`src/tools/java/dev/tip/tools` is its own Gradle source set (`tools`), not in the app jar. It compiles against the app's classes and dependencies. `./gradlew fakeDevice --args="--url=ws://localhost:8080 --device=<uuid> [--secret=<secret>]"` runs `FakeDevice`, which reads `.env` like `bootRun` and falls back to `TIP_DEMO_DEVICE_SECRET`. `FakeDevice` (JDK `HttpClient` WebSocket, listener, acks every reaction on receipt including repeats it does not play, reads `repeats` with missing as 1 and clamping, prints a `closing` reason and waits at least 60 s after `replaced`, stops on 401), `Player` (queue of 4, drop oldest, plays in order), `LedPattern` (protocol units, gaps, base units, scaled lengths and a text picture), `RecentIds` (last 16 tip ids), `Backoff` (1 to 30 s, up to 20 % jitter).

`./gradlew aiEval` runs `AiEval`: it binds `tip.ai.*` from `application.properties` and the environment (`.env` loaded by the task), builds the production classifier through `dev.tip.ai.EvalClassifier`, runs the labelled cases in `src/tools/resources/ai-eval-cases.jsonl` (message, kind or a list of accepted kinds, flagged, ownerNote `true`, `false` or `"ifRequest"`) one by one against the real model, and prints each disagreement and accuracy for kind, flag, owner note and all three. It decodes each line as strict UTF-8 and fails with the line number on a malformed byte or a broken line. The cases include prompt injection attempts (fake system lines, fake JSON results, delimiter breakouts, owner impersonation, one in French). Without a key it exits with a message. Never part of `build`, `check` or CI.

Every `JavaExec` task runs with `-Dstdout.encoding=UTF-8` and `-Dstderr.encoding=UTF-8`: Gradle reads a tool's output as UTF-8, and a JVM writing to a pipe on Windows otherwise encodes in Cp1252, which turned `ö` into U+FFFD. `.editorconfig` and `.gitattributes` keep text files UTF-8 with LF (CRLF for `.ps1` and `.bat`). Windows PowerShell 5.1 still needs `[Console]::OutputEncoding = [Text.Encoding]::UTF8` to display the output.

## Firmware

`firmware/` is a PlatformIO project for the physical panda (ESP32 DevKit `esp32dev`, Arduino core 3.3.12 through the pioarduino platform pinned in `platformio.ini`, partition table `huge_app.csv`). It sits outside the Gradle build: nothing in `build.gradle.kts` or Spotless reads it, and `firmware/.pio/` is git ignored. CI builds it and runs its native tests in the `firmware` job. `firmware/README.md` has setup, secrets, build, flash, monitor, test, the library choice and the TLS statement.

- `include/tip_config.h` (committed): server host and port, device slug, SNTP servers and every timing and limit. `include/secrets.h` (git ignored, template `secrets.example.h`): WiFi, `TIP_DEVICE_ID`, `TIP_DEVICE_SECRET`; the build stops without it.
- `lib/tip_core/` (plain C++, no Arduino includes, Unity tests in `test/` run with `pio test -e native`): `tip_protocol` (parse server messages from a filtered 256 byte `StaticJsonDocument`, build acks), `tip_intake.h` (`RecentIds` ring of 16, ack always and play once), `tip_player.h` (queue of 8 dropping the oldest waiting, LED level over time), `tip_patterns` (the four patterns with the virtual panda's step timings, status flicks), `tip_link` (backoff, silence check, HTTP status line, certificate dates).
- `src/main.cpp` starts two tasks on core 1 joined by a FreeRTOS queue of `tip::Reaction`: `network_task.cpp` (`net`, priority 2: WiFi, SNTP, WebSocket state machine, ack, hand over) and `playback_task.cpp` (`led`, priority 3: the only code that writes the LED, every 10 ms).
- `src/secure_transport.cpp` is the TLS client under links2004/WebSockets 2.7.1 in `NETWORK_CUSTOM` mode: `NetworkClientSecure` with the built in CA bundle and hostname check, then the validity dates of every presented certificate against SNTP time before the library sends the upgrade request; it also reads the HTTP status line, so a 401 stops reconnects.

Device side of the protocol: connect to `wss://<host>/ws/device/{deviceId}` with `Authorization: Bearer <secret>` and no `Origin`; `hello` is logged; each `reaction` is validated (lowercase uuid id, known kind or `PLAIN` x1 for an unknown one, `repeats` missing or not an integer as 1, clamped to 1 to 5), acked with `{type: ack, id}` on receipt, and played unless its id is among the last 16; `closing` is logged and `replaced` makes the next wait at least 60 s; anything else is logged, malformed messages are not acked. Nothing received for 45 s closes the connection. Reconnects back off from 1 s doubling to 60 s with up to 20 % jitter taken off, reset only after a connection stayed up 60 s.

## How a refund flows

1. A signed in owner posts `/api/owner/tips/{tipId}/refund` with the CSRF token.
2. `TipRefundService` checks the tip's device belongs to the owner through `DeviceDirectory.isOwnedBy` (404 otherwise) and that it is `CAPTURED` (409 otherwise).
3. `PayPalGateway.refundCapture` refunds in full with request id `refund-<tipId>`. `COMPLETED` (or `CAPTURE_FULLY_REFUNDED`) runs `TipTransitions.refund`; `PENDING` answers 202 and the `PAYMENT.CAPTURE.REFUNDED` webhook runs the same transition later.

## Startup seeding

`DemoDeviceSeeder` creates the demo owner through `OwnerProvisioning` when the email is new, then creates the demo device or reassigns it to that owner and updates its secret hash from `TIP_DEMO_DEVICE_SECRET`. It refuses a secret that is clearly not random and logs the demo device id, never the secret.

With the Spring profile `dev` (local runs only; Render never sets it), `DevTipSeeder` adds 40 invented sample tips to the demo device on `ApplicationReadyEvent`, which comes after every `ApplicationRunner`, so the demo device exists by then. Each sample has a fixed PayPal order id `DEV-SEED-01` to `DEV-SEED-40` and is inserted with `ON CONFLICT (paypal_order_id) DO NOTHING`, so a later run adds nothing. The samples cover the four kinds and the four visible statuses, flagged tips with a reason, requests and feedback with owner notes and tips without a message, eight hours apart over the last 14 days. Captured samples are stored as already classified (`DONE`, or `SKIPPED` without a message), so the AI recovery job never takes them, and no reaction is sent for them. Without a demo device it logs a warning and adds nothing. It inserts into `tip` directly with its own SQL, so any migration that changes the columns of `tip` must update `DevTipSeeder` too.
